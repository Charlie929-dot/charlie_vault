HTTP（HyperText Transfer Protocol，超文本传输协议）是互联网上应用最广泛的网络协议之一。它基于 TCP 协议，采用请求-响应模型，并具有无状态、可扩展等特点。以下为您详细解析 HTTP 协议中的请求头、响应状态码以及 Cookie/Session 机制。

### 一、 HTTP 请求头（Request Headers）

HTTP 请求报文由请求行、请求头、空行和请求体组成。请求头由多个键值对组成，用于向服务器传递客户端的附加信息、偏好或上下文状态。常见的请求头包括：

- **Host**：指定请求的目标主机和端口号。
- **Content-Type**：说明请求体的媒体类型（如 `application/json`）。
- **Content-Length**：请求体的字节长度，用于服务器确定读取边界。
- **User-Agent**：标识客户端软件信息（如浏览器类型）。
- **Accept**：指定客户端能够接受的 MIME 类型（如 `text/html`）。
- **Cookie**：携带客户端的会话信息，是维持 HTTP 状态的重要请求头。
- **Authorization**：包含用于验证用户身份的授权凭证。

### 二、 HTTP 响应状态码（Status Codes）

响应状态码是服务器响应客户端请求时返回的三位数字代码，用于表示请求的处理结果。状态码由 RFC 规范定义，分为五大类：

1. **1xx（信息性响应）**：请求已被接收，继续处理。例如 `100 Continue` 表示客户端应继续发送请求主体。
2. **2xx（成功）**：请求已成功被服务器接收、理解并处理。最常见的是 `200 OK`；创建新资源成功通常返回 `201 Created`。
3. **3xx（重定向）**：需要进一步操作以完成请求。例如 `301 Moved Permanently` 表示资源已永久移动，`302 Found` 表示临时移动。
4. **4xx（客户端错误）**：请求有语法错误或参数无效，服务器无法处理。例如 `400 Bad Request`（请求错误）、`401 Unauthorized`（未授权）、`404 Not Found`（资源不存在）。
5. **5xx（服务器错误）**：服务器在处理请求时发生错误。例如 `500 Internal Server Error`（服务器内部通用错误）、`502 Bad Gateway`（网关收到无效响应）。

### 三、 Cookie 与 Session 机制

HTTP 协议本身是**无状态**的，即协议不记录事务处理过程中的状态信息，每个请求都是独立处理的。为了支持用户登录、购物车等需要持续状态的动态 Web 应用，引入了 Cookie 和 Session 机制。

#### 1. Cookie（客户端状态保持）

- **定义**：Cookie 是服务器发送到用户浏览器并保存在本地的一小块数据。
- **工作原理**：服务器在 HTTP 响应头中添加 `Set-Cookie` 选项，浏览器收到后会将其保存在本地。之后，浏览器在向同一服务器发起请求时，会通过 `Cookie` 请求头携带这些数据发送给服务器。
- **用途**：主要用于会话状态管理（如保持登录状态）、个性化设置（如主题偏好）以及浏览器行为跟踪。
- **生命周期**：分为会话期 Cookie（浏览器关闭后删除）和持久性 Cookie（在指定的过期时间 `Expires` 或有效期 `Max-Age` 之后被删除）。

#### 2. Session（服务器端状态保持）

- **定义**：Session 是客户端与服务器通过多次 HTTP 请求维持关联的交互过程，其数据存储在服务器端（如内存、数据库或 Redis）。
- **工作原理**：会话创建时，服务器生成一个全局唯一的 Session ID，并通过响应头（如 `Set-Cookie`）传递给客户端。客户端在后续请求中自动携带该 Session ID，服务器据此查找对应的 Session 数据以实现状态连续性。
- **优势**：敏感信息（如用户凭证）仅保存在服务器中，客户端只需传递 ID，相比 Cookie 具有更高的安全性；且不受客户端存储大小的限制。

**总结**：Cookie 和 Session 并非互斥关系。在实际应用中，Session 常常依赖于 Cookie 来实现客户端与服务器之间的关联（即通过 Cookie 传递 Session ID），两者共同弥补了 HTTP 无状态协议的不足。
